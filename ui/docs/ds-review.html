Redesign proposal

New dashboard

The current dashboard is written for a machine to read: raw ids, long numbers without units, a hard-to-follow node diagram, and several overlapping pages. The new one is light, compact, in Linear's style, with a dark mode. Every page speaks in plain words: what's happening, where it stands, and what needs you. The sidebar is down to 5 items. What needs you sits right at the top of the home page. This very page uses the new palette, so you're previewing the interface live; the "Switch light / dark" button is at the top.

Needs you: approve to start the first PR (DS0).

Page shell

The sidebar is down to 5 items; each item carries an icon and a label. "Work" is the one exception: it always shows two indented children, "Kanban" and "Roadmap", below it. The open item (or open child) has a grey background and a colour stripe on the left text, not blue; when a child is open, "Work" itself turns bold with no fill, so the section and the page inside it never look like one block. In dark theme, the sidebar's logo mark sits on a faint white backing plate that grows outward around it; in light theme there is no plate. The top bar has a single "Live" light, replacing today's two clocks and two refresh buttons. Beside the light are four icon-only buttons: pause, refresh (disabled while auto-updating), switch theme, and settings. Hovering or tabbing to any button shows a tooltip with its name.

Collapsed, the rail drops "Work"'s children entirely; when the open page is Kanban or Roadmap, "Work" itself shows as the active item instead.

Text inside the mocks is kept in English, matching what the dashboard will show: every piece of interface copy is English; the explanation around it is in plain prose. The figures come from the design draft (read from the running dashboard on 30 Sep). An "agent" is an AI session playing one role (coder, tester, ...). A "token" is the unit that measures model usage, i.e. cost.

Three shared states for every page

  • Loading: shows a grey placeholder block. Never shows a "0" before real data arrives.
  • Empty: a specific sentence for that page, e.g. "Nothing needs you right now." No more generic sentences that turn out false.
  • Error: a red banner "Could not load <page>", with a "Retry" button and a collapsed detail section.

When an old record can't be read, the top banner says so in plain words: "1 old record (csb-audit-1, 7 Sep) could not be read; totals may be slightly low." The technical detail sits behind the "Details" button.

Each page: before and after

Home page, with the "Needs you" box

Before
  • What needs you is scattered across the side rail, easy to miss.
  • Overview and Projects are two separate pages.
  • Raw numbers like "≥127113770 tok", "4pp".
  • A finished epic still shows as running.
After
  • A "Needs you" box sits at the top of the page, merging 4 kinds into one filterable list.
  • "Running now" groups by project, with a "Just finished" row.
  • Readable numbers: "127M of 180M tokens (71%)", "4 points lower than an hour ago".
  • "What the factory decided recently" written in plain words.

Four kinds: a waiver (you agreed to skip a finding that was raised), an escalation (the factory couldn't handle it on its own), a stop point (where the factory halts to wait on your decision), and a proposed lesson awaiting approval.

The "Needs you" box is split by project: each project gets a group header naming it and the item count ("shop-api · 2"). The group with the most urgent item comes first; a project with nothing waiting doesn't show. When the top bar has a project selected, the box shows exactly that project's one group (the header still shows). Proposed lessons not tied to any project live in the "All projects" group.

Each item has two lines of text: a short title naming the decision needed (e.g. "Approve waiver for 2 minor findings"), and below it one description line in faint text, saying why the factory stopped and what happens once you act (e.g. "Checkout flow · review found 2 style issues; merge is waiting on you"). A description longer than one line is cut with "…"; hover (or use a screen reader) to read the full sentence. The right side still carries the related project or task and the time. An item you haven't seen has a blue dot ("Unread") and a bolder title; a seen item is regular weight. The "Unread" mark is remembered right in each viewer's browser, not stored on the server, so each person has their own state. On first open, every item is "Unread". Each row's button also shows when you tab to that row by keyboard, not only on hover.

The "stop point" kind has no data source yet. If no place to record it turns up, this box ships with 3 kinds, and the fourth kind lands in a later PR.

Below the "Needs you" box sits a "Recent activity" block: the 8 latest events, built with the exact same row component as the Activity page (TimelineRow), so the two places can never drift apart. Each row: title with a kind label, below it a faint line with up to 4 fields (e.g. "Round 2 · Running for 12 s"), and a chevron at the end of the row to open the detail section (reason, task, model, tokens…). Every row is closed by default; in the example the first row is open. No leading icon. It differs from the Activity page in two ways: no "Expand all" button, and only 8 rows. The block auto-updates at the same pace as the page, and the "View all activity" link opens the Activity page.

Work: the Kanban board

Before
  • The card title is a whole description, about 400 characters long.
  • A task silent for more than 24 hours still reads "In progress".
  • Clicking a card jumps straight to the detail page.
  • Every card repeats the status, even though the column already says it.
After
  • Every card has exactly 5 fixed rows, so the whole board reads evenly.
  • A chip only shows when it adds new information. If the column is already "Blocked", the card does not repeat "Blocked". At most 2 chips, the rest fold into "+N".
  • Agent chip: role + status ("working", "reviewing", "waiting", "idle"). "waiting" comes with a hint, "a nudge may help".
  • Clicking a card opens a quick-look panel beside it first, with an "Open full page" button.
  • "Display" option: toggle the one-line summary, change column grouping, hide columns.
  • The "Completed (109)" column is collapsed by default.

The five rows of a card, top to bottom:

  1. Short task id (faint) and agent chip.
  2. Title, at most 2 lines, truncated beyond that.
  3. A one-line summary. Can be turned off in "Display".
  4. A chip, only when it adds information: task type, severity if above default.
  5. Role on the left; on the right, "Attempt 2" if retried, otherwise "updated X ago".

Below row 5 is the card footer, not counted among the 5 rows: which task it is waiting on, a comment count, "Open PR" if any, a screenshot count if any.

One-line summary.

Open full page

Each grouping (by project, epic or role) also adds a "None" column for tasks missing that information. A hidden column can always be shown again from "Display". The "Display" choice is remembered in your browser; if the browser does not allow saving, the board uses defaults: summary on, grouped by status, no columns hidden. A column with too many cards (over 30 by default) only renders the visible part, so the page stays fast.

Keyboard use: up/down arrow keys move between cards in a column, left/right move to the next column. Space or Enter opens the quick look, Esc closes it and returns you to the card you just opened.

The quick look also has a "Requested by you" block like the detail page (see below). In the example, the latest request is just "continue", a generic nudge, so the panel also shows "Epic started from": the request that opened the epic.

Cards cannot be dragged, and that is intentional. Only the factory changes a task's status, so the board does not let you drag a card to another column or reorder it. Right-click (or long-press on phone) opens a view-only menu: "Open full page", "Open PR", "Copy id".

The "waiting" threshold is a single constant (24 hours), or taken from the project's configuration if the project declares one.

Work: the roadmap (merging the epic page too)

Epic is a large block of work, split into several waves that run in sequence. Phase groups several epics around one goal. Roadmap and epic used to be two pages; the new version merges them into one, so "Work" now has only two modes: "Kanban / Roadmap".

Before
  • A drag-and-drop node diagram, hard to read, on both the roadmap and the epic's "Flow" page.
  • Roadmap and epic are two pages; seeing an epic's waves means leaving the roadmap.
  • The shop-api project has more than 10 epics but reports "no project worked on yet".
  • A phase with no tasks shows "0/1 (0%)".
  • Relationships between tasks are written as technical codes.
After
  • On top: a month-based swimlane. Each phase is one row, its epics are indented child rows. There is a red "Now" line. Past bars are faint, the current one is solid, upcoming ones are dashed ("not scheduled" if there is no date yet).
  • Below: one epic block, replacing the old detail table. Selecting a row changes the block accordingly.
  • Selecting a phase: goal, "13 of 25 tasks done", a multi-colour progress bar, completion condition. Then one item per epic: name, status, progress and the wave list. The running epic opens by default, the others collapse.
  • Selecting an epic: name, project, status, progress, the request that opened it, a plan-version picker "Plan: latest (v12) / earlier drafts", then the wave list.
  • Each wave is one row: "Wave 12 of 18 · 6/8 done" and a progress bar. The current wave is open and highlighted; past waves collapse; upcoming waves are dashed.
  • Relationships in plain words: "uses its output", "edits the same files", "its test guards this".
  • "No tasks tracked" replaces "0/1".

Thirteen ideas learned from multica

multica is another dashboard, also for dispatching work to AI agents. We looked at how it works and borrowed thirteen ideas, split into three groups.

Group 1: the five original ideas

  1. A single "needs you" list at the top of the page, replacing several scattered small boxes.
  2. A run timeline for each task: attempts, judge rounds, outcome.
  3. An agent chip on the card, with its own "waiting" state for an agent that has gone quiet.
  4. A quick-look panel that opens beside the card before moving to the full page.
  5. Activity loads by page, loading more as you scroll; now with self-update, kind labels, and a "because of" link.

Group 2: four ideas for the Kanban board

  1. A fixed 5-row card, chips only show when they add information, up to 2 chips then "+N".
  2. Changing how columns are grouped (status, project, epic, role), with a count and a "Hide column" menu on each header.
  3. A "Display" box: toggle the summary, the grouping, hidden columns; remembered in the browser.
  4. Moving between cards with arrow keys, Space/Enter opens the quick-look, Esc closes it.

Deliberately skipped: dragging cards between columns, because here only the factory is allowed to change a task's status.

Group 3: four newly approved ideas

  1. A 7/30/90-day period switch on the Cost page, with charts of tokens by day and by role.
  2. Tokens and duration for each task, placed right on the run timeline.
  3. An "Unread" mark in the "Needs you" box, remembered separately per viewer.
  4. Agent workload status, naming the "queued too long" case separately.

Not taken

  • Scheduled runs: the factory already decides on its own when to run a task.
  • Flexible AI team: each agent's role is set by the factory, not by the dashboard.
  • Bulk edit: this dashboard is view-only, it does not edit tasks.
  • Gantt chart: the monthly-lane roadmap is already enough.
  • Saved filters: the "Display" box already remembers your choices.
  • "My tasks": work is assigned to agents, not to individual people.

Only the ideas were borrowed. No code, component names, copy, colors, or images were taken, because multica's license has conditions about branding and hosting. None of the ideas add a new event kind or a new place to write to; some need the server to return data it already has (see "Build order").

Technical details

For readers of the code
  • The token prefix changes from --ds- to --bs-. Files: ds-tokens.css becomes bs-tokens.css, ds-components.css becomes bs-primitives.css.
  • New component directory: ui/src/components/kit/, replacing ui/src/components/ds/ (removed in DS9). No new npm dependency.
  • @vue-flow/core is removed from package.json in DS9, after Flow, Roadmap, and Sessions stop using the node diagram.
  • DS0 updates the check scripts: check_tokens.py, lint_hardcodes.py, contrast_check.mjs (rewriting the color-pair list). They scan both the old and the new set until DS9. check_no_emoji.py and scripts/check.sh are unchanged.
  • New, read-only endpoints: GET /api/inbox (DS2), GET /api/tasks/:taskId/runs (DS3), GET /api/timeline?before=&limit=&after= (DS6; after=<eventId> marks where to fetch the new part on repoll). Each timeline row returns an extra nearestPromptId, and for a dispatch, its merged run result (input/output tokens, duration, outcome).
  • Nearest prompt: a new read function in queries.ts, recursing through causal_parent to the nearest user_prompt; the epic-opening prompt is the earliest user_prompt in the epic's session chain. Returned at /api/tasks/:taskId, in the epic/roadmap data, and on /api/kanban rows (flag + first line). dispatches.parent_prompt_id is unused because it has never been written.
  • Self-update uses the existing usePoll: triggered by /api/stream, repolling every 15 seconds when the stream drops, stopping when the tab is hidden. No websocket.
  • The old /roadmap and /flow?epic= routes redirect to /work/roadmap and /work/roadmap?epic=. There is currently no /epic/:id route.
  • /api/analytics (DS7) accepts a new period parameter (7d/30d/90d), returning a daily token series (by role or by model kind) and a table split by role/model kind for the chosen period. These endpoints read back already-stored task-result-recorded rows; the "not measured" count reuses the existing unmeasuredTaskCount. cost_usd still never goes past runner.ts:99/:212.
  • /runs (DS3) additionally reads token_usage and the duration of each run when the event has it, and returns a totals table by role (run count, tokens, duration). When absent, it returns "not measured".
  • /api/kanban (DS3) returns more for each row: updatedAt, attemptCount, judgeRound, commentCount, prUrl, dependencies, project key. New constants: KANBAN_VIRTUALIZE_THRESHOLD (30 by default, ui/src/lib/constants.ts), agentWaitingThresholdMs.
  • KanbanDisplayOptions and the "Unread" mark of the "Needs you" box are stored in localStorage, read/write wrapped in try/catch, falling back to defaults on error.
  • AgentStatusBadge (DS8) only reads agentActivity and agentWaitingThresholdMs. agents-registry.ts has no heartbeat signal, so there is no "presence" axis yet.
  • Notable new components: TaskCard, WaveList, RoadmapSwimlane, NeedsYouInbox, AgentChip, RunHistoryTimeline, TaskPeekPanel, LiveIndicator, KanbanDisplayOptions, PeriodSwitch, AgentStatusBadge, EpicBlock, RequestQuote, TimelineRow (one component for Activity, Recent activity on Home, and a task's history). New tokens: --bs-event-<kind>-text / --bs-event-<kind>-subtle for 9 event kinds, added to the pair list of contrast_check.mjs.
